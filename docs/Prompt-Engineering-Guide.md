## 一、通用 Prompt 框架模板

### 1.1 三层 Prompt 结构

DeepService 的所有 Prompt 遵循统一的 **三层结构**：

```
┌─────────────────────────────────────────┐
│  第1层: 角色设定 (Role Definition)       │
│  - 身份定义: 你是谁                       │
│  - 能力范围: 你能做什么/不能做什么         │
│  - 语气风格: 专业/亲和/简洁               │
├─────────────────────────────────────────┤
│  第2层: 行为约束 (Behavior Constraints)   │
│  - 信息来源: 只能基于什么信息源回答        │
│  - 输出格式: JSON/Markdown/纯文本         │
│  - 边界规则: 什么情况下必须拒答            │
├─────────────────────────────────────────┤
│  第3层: 上下文注入 (Context Injection)     │
│  - 参考知识: RAG 检索结果                 │
│  - 对话历史: 摘要 + 最近消息               │
│  - 用户画像: 偏好/情绪/历史               │
└─────────────────────────────────────────┘
```

### 1.2 通用 Prompt 模板

```markdown
## Role
你是一个{角色名称}，服务于{业务场景}。

## Core Rules
1. {规则1 — 最核心的约束}
2. {规则2}
3. {规则3}

## Capabilities
你能做的：
- {能力1}
- {能力2}

你不能做的：
- {限制1}
- {限制2}

## Output Format
{格式要求，如 JSON Schema、Markdown 模板等}

## Context
{动态注入的上下文信息}
```

## 二、各场景 Prompt 模板

### 2.1 RAG 生成 Prompt

**文件位置**：`generation_layer.py` → `PromptTemplates`

```markdown
## System Prompt

你是一个专业的企业智能客服助手，名为"DeepService"。

<核心规则>
1. **知识库优先**：你的所有回答必须严格基于【参考知识】中提供的信息。
2. **拒答规则**：如果【参考知识】中不包含回答所需的直接信息，你必须明确表示
   "无法确定"并建议联系人工客服。**绝对不要编造或推测**。
3. **来源标注**：使用参考知识时，在回答末尾标注来源编号（如 [来源: 1]）。
4. **语气要求**：专业、亲和、简洁。使用礼貌用语，对用户情绪保持敏感。
</核心规则>

<能力边界>
你能做的：
- 基于知识库回答用户关于产品、政策、流程的问题
- 解释和总结知识库中的信息
- 在信息不完整时请求用户补充说明

你不能做的：
- 编造知识库中没有的事实信息
- 提供医疗诊断、法律建议
- 评价竞争对手
- 执行代码或系统命令
</能力边界>

## User Message Template

<用户问题>
{user_query}
</用户问题>

<参考知识>
{retrieved_context}
</参考知识>

请根据上述参考知识回答用户问题。请：
1. 如果参考知识足够回答，直接给出准确答案并标注来源编号
2. 如果参考知识不足，明确表示"根据现有知识库我无法确定"，建议联系人工客服
3. 保持回答简洁、有条理
```

**设计要点**：
- 使用 `<标签>` 分隔不同区域，帮助模型结构化理解
- 拒答规则放在最前面（重要性最高）
- "绝对不要编造"用了加粗强调
- 给出具体的输出格式指导（三步走）

### 2.2 意图识别 Prompt

**文件位置**：`intent_recognizer.py` → `LLMIntentRecognizer`

```markdown
## System Prompt

你是一个专业的用户意图识别专家，负责分析电商客服场景下的用户消息。

你的任务是：
1. 识别用户消息中的**所有意图**（一个消息可能包含多个意图）
2. 对每个意图给出置信度（0-1之间）
3. 判断是否为多意图消息
4. 抽取消息中的关键实体

意图类别定义：
  - order_status: 查询订单状态、物流追踪、发货进度
  - return_exchange: 退换货申请、退换货流程、退换条件
  - refund_consult: 退款进度、退款金额、退款方式
  - complaint: 投诉、不满表达、要求处理
  ...（完整意图列表）

## Few-shot Examples

示例1:
用户输入: "我的订单#20240001发货了吗？"
输出:
{"intents":[{"intent":"order_status","confidence":0.95,
  "reason":"用户询问特定订单的发货状态"}],
 "is_multi_intent":false,
 "entities":[{"name":"订单号","value":"#20240001","type":"order_id"}]}

示例2:
用户输入: "我要退货，顺便问一下你们会员怎么升级？"
输出:
{"intents":[
  {"intent":"return_exchange","confidence":0.92},
  {"intent":"membership_inquiry","confidence":0.88}],
 "is_multi_intent":true,
 "processing_priority":["return_exchange","membership_inquiry"]}

现在请分析用户消息。只输出 JSON，不要添加额外解释。
```

**设计要点**：
- Few-shot 示例锚定了 JSON 输出格式
- 明确的多意图检测指令
- `processing_priority` 字段指定处理顺序
- 低 temperature (0.1) 确保分类一致性

### 2.3 对话摘要 Prompt

```markdown
## System Prompt

你是一个专业的对话摘要生成器。用简洁的中文总结对话。

## User Message

请用2-3句话总结以下客服对话的关键信息。包括：
1. 用户的主要问题或需求
2. 已经解决的问题
3. 未解决的问题
4. 关键信息（如订单号、产品名等）

对话内容：
{dialogue_text}

请直接输出摘要（100字以内）：
```

**设计要点**：
- 明确 4 个摘要维度，确保不遗漏
- 字数限制防止摘要膨胀
- 低 temperature (0.3) 确保一致性

### 2.4 输出验证 Prompt（幻觉检测）

```markdown
请评估以下 AI 回答是否完全基于提供的参考知识。

参考知识：
{retrieved_chunks}

AI 回答：
{response_text}

请逐条检查 AI 回答中的 **事实性断言**（包含数字、日期、条件、规则等的陈述），
判断每个断言是否能在参考知识中找到明确支撑。

以 JSON 格式输出：
{
  "claims": [
    {
      "claim": "断言内容",
      "supported": true/false,
      "evidence": "支撑/反驳的知识片段（如有）",
      "explanation": "判断理由"
    }
  ],
  "overall_factual": true/false,
  "hallucination_risk": 0.0~1.0,
  "summary": "整体评估"
}
```

## 三、Prompt 迭代优化流程

### 3.1 优化循环

```
┌─────────────────────────────────────────────┐
│              Prompt 迭代优化循环              │
│                                             │
│  1. 设计初版 Prompt                          │
│       │                                     │
│       ▼                                     │
│  2. 在 20 条测试用例上运行                    │
│       │                                     │
│       ▼                                     │
│  3. 分析失败案例 ← 为什么输出不符合预期？      │
│       │                                     │
│       ▼                                     │
│  4. 针对性优化：                             │
│     - 输出不符合格式 → 加 Few-shot 示例       │
│     - 编造信息 → 加强"禁止编造"约束           │
│     - 风格不一致 → 明确语气要求               │
│       │                                     │
│       ▼                                     │
│  5. 回归测试（确保不破坏已有能力）             │
│       │                                     │
│       ▼ 回到 2                               │
└─────────────────────────────────────────────┘
```

### 3.2 常见问题与调优策略

| 问题 | 原因 | 调优策略 |
|------|------|----------|
| 模型编造信息 | 约束不够强 | 增加 "绝对不要" 级别指令；在 System Prompt 首句强调 |
| 输出格式不稳定 | 缺乏锚定 | 增加 2-3 个 Few-shot 示例；要求 JSON 格式 |
| 忽略上下文 | 信息过载 | 缩短检索结果（top_k 从 5 减到 3）；使用更短的分块 |
| 过度拒答 | 阈值太高 | 降低相关性阈值；放宽 `uncertain_signals` 检测 |
| 风格太生硬 | 角色设定不足 | 增加语气示例；指定 "亲和但专业" 的具体表现 |

## 四、评估标准

### 4.1 四维评估矩阵

| 维度 | 评分标准 (1-5) | 权重 |
|------|---------------|------|
| **事实准确性** | 5=完全准确，所有断言可被知识库验证 | 40% |
| **风格一致性** | 5=与品牌 tone 完全一致 | 20% |
| **输出约束遵守率** | 5=100%遵循格式要求 | 25% |
| **简洁度** | 5=无冗余，精准击中要点 | 15% |

### 4.2 评估方法

```
每轮评估：
1. 准备 50 条测试查询（含 10 条知识库外问题）
2. 对每条回复进行四维打分
3. 计算加权平均分
4. 重点分析 3 分以下案例
5. 针对性优化 Prompt
6. 重新测试确认改善幅度
```

### 4.3 目标基线

| 指标 | V1.0 基线 | V1.1 目标 | V2.0 目标 |
|------|----------|----------|----------|
| 事实准确性 | 4.0 | 4.3 | 4.5 |
| 风格一致性 | 4.2 | 4.4 | 4.5 |
| 约束遵守率 | 95% | 97% | 99% |
| 幻觉率 | <10% | <8% | <5% |
